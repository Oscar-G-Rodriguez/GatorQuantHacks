# H22 — Debt financing resolution and covered calls

This Massive-track strategy has completed its first registered HiPerGator development backtest. The [verified results](Results.md) are **INCONCLUSIVE**: one primary event trade earned$861.03 after assumed costs, versus$1,193.08 for the same stock, with zero complete ordinary-date matched pairs. The fixed completion sample is too small to establish a trading edge. Statistical null calibration failed and inferential claims are suppressed.

Read [the strategy brief](Hypothesis.md), [complete experiment plan](Experiment%20Plan.md), [research log](Research%20Log.md), [H21 findings](../H21%20-%20Massive%20Disclosure%20Research%20Atlas/Stock%20Readout.md), [Massive track route](../../../Massive%20Track/README.md) and [repository rules](../../AGENTS.md). The complete protocol fixes the consequential choices before code; the earlier proposal commit alone did not supply registration.

The proposed rule is to identify an affirmatively completed debt issuance, wait for usable label availability, and test a funded stock position with a same-name covered call. Fixed starting choices are approximately 120 calendar days to expiration, a strike about 5% above nominal spot, and a 21-session holding period. Compare with the same covered call on matched ordinary dates and with unhedged stock. All sponsor horizons and bounded maturity, strike, cost and delay checks remain required.

Code and data preparation stay on the PC; scientific calculations and any subsequently authorized trading simulation use scheduled HiPerGator allocations. Shared credentials, dependencies and runtime stay at the repository root. The complete protocol was registered as `8c3e4e4` before implementation. `backtest.py` owns the phase/stage interface; `research.py` prepares fixed event/control anchors, and `pipeline.py` freezes, packages, generates scheduled jobs and verifies returned files. Read the complete experiment plan before using these interfaces. The preparation stage produces coverage without evaluating subsequent returns.

`acquire.py --prepared <verified-preparation>/prepared --output <new-acquisition>` downloads bounded Massive data on the PC with the root credential. It retains immutable objects, pagination/error receipts and resume status. It does not fit or backtest. Review acquisition coverage before freezing a backtest input, and never overwrite a frozen run to repair a failure.

For a backtest freeze, place the verified `prepared/`, original `input/source/`, and completed `acquisition/` inside a new directory under `data/cache/h22/`. Keep earlier manifests/receipts in `provenance/`, separate from this run's active receipts. From the repository root, run `pipeline.py freeze --run <new-run> --phase backtest`, followed by `pipeline.py bundle --run <new-run> --output <new-archive.tar.gz>`. The manifest records registration, code/settings/source hashes and all24 fixed tasks. Upload both archive and generated installer into private Blue storage, check their whole hashes, and install to the unique destination recorded in the manifest.

Submit the generated `hpg/pilot.sbatch` first. After successful scheduler states and measured resource evidence, submit `hpg/run.sbatch`; completed pilot tasks reuse verified checkpoints. Download the returned archive and use `pipeline.py import --run <new-run> --archive <download> --sha256 <remote-whole-hash>`; whole and member hashes must verify before results are interpreted.
